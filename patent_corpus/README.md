# 专利导出 → 中文能源电力训练语料

把佰腾 / 专利之星等数据库导出的 Excel/CSV，转成干净的、领域聚焦的中文训练语料。

**本工具不联网**，只处理你自己导出的文件。数据来源的合规性由你和你的数据库账号决定。

---

## 一、先读这段：GB 量级的账

中文 UTF-8 下一个汉字占 3 字节，所以「要多少件才够 1GB」完全取决于导出时勾了哪些字段。

下表第一行是**从真实导出文件（专利之星）实测**的数字，其余为按比例的推算：

| 导出包含 | 每件约 | 到 1GB 需要 |
|---|---|---|
| 摘要 + 主权项（**实测：260 + 428 字**） | **2,283 字节** | **约 47 万件** |
| 摘要 + 完整权利要求书（~2000 字） | ~7 KB | 约 15 万件 |
| 摘要 + 权利要求书 + 说明书（~5000 字） | ~17 KB | **约 6 万件** |

**结论：现在的导出格式（摘要 + 主权项）要 47 万件才够 1GB，这不现实**——
按每批 500 件算要导出 900 多次。

### 两个能显著改善量级的动作

1. **导出时找找有没有「说明书」或「全文」字段。** 说明书通常 3000~8000 字，
   加上它能把需求从 47 万件降到 6 万件左右。
2. **优先导「发明专利」而不是「实用新型」。** 实用新型不经过实质审查，说明书短、
   权项少、技术含量低；发明专利的说明书和权利要求书都完整得多，训练价值高得多。

顺带说，权利要求书和说明书的文本质量本来就比摘要高：摘要是压缩过的概述句，
权利要求书和说明书才是完整的、有层次的技术叙述。

工具每次运行都会报告实际体量和「按当前每件体量到 1GB 还需多少件」，可随时校准。

## 二、快速开始

```bash
PY=/root/miniconda3/envs/autodl-tmp/bin/python
cd /root/autodl-tmp/energy_rag

# 1. 先检查列识别和领域判定（务必先做这步）
$PY -m patent_corpus inspect ~/patent_exports/

# 2. 确认无误后构建语料
$PY -m patent_corpus build ~/patent_exports/ \
    --out corpus/ \
    --jsonl patents.jsonl \
    --single corpus-all.txt
```

**第 1 步不能跳过。** 列识别错了会把权利要求书当摘要用，产出的语料直接报废，
而且这种错误不会有任何报错提示，只有肉眼能发现。

## 三、命令

### `inspect` —— 检查（不产出文件）

```bash
$PY -m patent_corpus inspect <文件或目录> [--limit 200]
```

报告三件事：

1. **每个文件识别到了哪些列** —— 和我支持的 15 个规范字段逐一对齐；
2. **未使用的列** —— 如果你导出了我没识别的字段，会列出来；
3. **领域判定抽样** —— 随机看几条，显示收录/筛除以及判定依据。

如果收录率低于 5%，会提示你检查是否勾选了 IPC 分类号字段。

### `build` —— 构建语料

```bash
$PY -m patent_corpus build <文件或目录> \
    --out corpus/            # 每件一个 .txt
    --jsonl patents.jsonl    # 结构化记录
    --single corpus-all.txt  # 全部拼进一个文件
    [--no-description]       # 不含说明书全文
```

三个输出参数至少给一个。

## 四、领域筛选是怎么做的

**按 IPC 分类号筛，而不是按关键词。** IPC 是人工标引的，比关键词可靠得多——
用「电力」做关键词会漏掉写「电网」「配网」「变流器」的，也会误收「电力猫」这类消费电子。

### ⚠️ 只看主分类号，不看完整分类号

这是从你的真实导出数据里发现的坑：

```
一种NFC近场供电解锁的U形锁
  主分类号：E05B67/22（锁）
  分类号  ：E05B67/22;E05B67/18;E05B47/00;E05B67/00;H02J50/10  ← 注意最后这个

一种揉锤按摩机芯和按摩器械
  主分类号：A61H7/00（按摩）
  分类号  ：A61H7/00;A61H23/02;H02K7/075;H02K7/116        ← 注意最后这两个
```

这两件**都不是电力专利**，只是一个用了无线供电、一个用了电动机，副分类号里才带了 H02。

**如果拿完整分类号做判定，这类无关专利会被成批误收进语料。** 所以领域判定只看主分类号，
完整分类号保留在 `ipc_all` 字段里供人工复核。

分类号分两类处理：

**严格分类**（命中即收录）：

| 分类号 | 含义 |
|---|---|
| H02* | 发电、变电、配电 |
| H01M | 电池、燃料电池 |
| F03D | 风力发电机 |
| F03B / F03G | 水力 / 其他能源机械 |
| F01K / F01D / F02C | 蒸汽动力 / 汽轮机 / 燃气轮机 |
| F22B / F22G | 蒸汽发生 / 过热 |
| F24S / F24T | 太阳能集热 / 地热能 |
| G21* | 核物理、核工程 |
| C10L | 燃料 |

**宽泛分类**（**必须配合关键词才收录**）：

| 分类号 | 为什么宽泛 |
|---|---|
| H01L | 半导体器件——光伏在这里，但所有芯片也在 |
| H01G | 电容器——超级电容在这里，但普通电容也在 |
| H23 / F24H / F28D | 燃烧 / 加热 / 换热——跨领域通用 |
| B60L | 电动车辆 |
| G01R / G05F / H01B | 电测量 / 电压调节 / 电缆 |
| C25B | 电解制氢 |
| C01B | 非金属元素——制氢在这里，但不止 |

不加这层限制的话，H01L 会把所有半导体专利都当光伏收进来。

**没有 IPC 字段时**退回关键词判定，并在记录的 `domain_reason` 里如实写明
判定依据是「无 IPC，关键词『电力』」，便于事后抽查。

每条记录都保留 `domain_reason`，你可以据此复核筛选是否正确。

## 五、输出格式

### JSONL

```json
{"pub_number":"CN110123456A","title":"一种配电网故障定位方法","abstract":"...",
 "claims":"...","description":"...","ipc":"H02J13/00","applicant":"某某电力公司",
 "domain_reason":"IPC H02J（供电或配电系统）","source_file":"导出_第一批.xlsx"}
```

### 纯文本语料

```text
公开号：CN110123456A，IPC：H02J13/00，申请人：某某电力科技有限公司

【发明名称】
一种基于深度学习的配电网故障区段定位方法

【摘要】
本发明公开了一种基于深度学习的配电网故障区段定位方法…

【权利要求书】
1.一种基于深度学习的配电网故障区段定位方法，其特征在于，包括：...
2.根据权利要求1所述的方法，其特征在于，...
```

每件一个 `.txt`，文件名是公开号——**稳定且唯一**，重复处理不会产生重复文件。

## 六、列名识别

不求你迁就固定的表头。工具维护了一张别名表，对表头做归一化（去括号、空白、大小写）
后模糊匹配。已覆盖：

| 规范字段 | 已支持的写法（部分） |
|---|---|
| title | 标题、名称、专利名称、发明名称、发明创造名称 |
| abstract | 摘要、专利摘要、摘要(中文)、中文摘要 |
| claims | 权利要求、权利要求书、主权项 |
| description | 说明书、说明书全文、描述 |
| pub_number | 公开号、公开(公告)号、公告号、专利号 |
| ipc | IPC分类号、主分类号、分类号 |
| applicant | 申请人、申请(专利权)人、专利权人 |
| … | 共 15 个字段 |

**匹配策略**：先精确匹配，再模糊包含，最后取最长别名命中——这样「摘要附图」
不会被误配到摘要列。

如果某列没识别出来，`inspect` 会告诉你。你可以把导出表头改成别名表里的写法，
或者改 `loader.py` 的 `COLUMN_ALIASES` 加上你的表头。

## 八、和 energy_rag 的关系

这批语料是**训练用**的（领域适应 / 继续预训练），和 energy_rag 的 RAG 检索语料
是两个用途，不要混。

如果你只想扩 RAG 语料，注意你现有语料才 191MB / 46 篇，几万件专利灌进去是严重过量，
会拖慢检索和重建索引。真要扩，挑高相关的几百到几千件即可，用 `--jsonl` 输出后
按 `domain_reason` 和年份再筛一轮。
